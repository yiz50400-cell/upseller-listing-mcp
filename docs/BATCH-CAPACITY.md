## 测试条件

- macOS arm64 / Node 26.8.1；现有 HTTP MCP 执行器，经本机已配置的显式代理。没有浏览器自动化或新客户端。
- 档位：2、4、8 个商品任务；每档只跑一个同等数量的突发批次，不是长时间稳定性压测。
- 同一个源商品、同一目标店、同一套 7 张原图共 19,298,490 字节；每个草稿 222 SKU。
- 每档独立冷缓存；批内相同原图按 SHA-256 合并上传，仅传 7 张，而非 7×商品数。没有压缩、缩放、转码或改动原文件。
- 商品准备并行，整批共用 3 路图片上传；同源同店复制排队，同店价格检查/保存/回读排队。

- 墙钟计时包含任务标准化、店铺/来源解析、原图上传、复制、保存和最终逐商品字段回读。

## 结论边界

- 可证实的仅是表中已经通过的档位；软件的 8 件保护上限不代表平台承载极限，也不代表 AI 只能处理 8 件。
- 软件默认商品并发为 8（已验证保护上限；固定分批屏障：≤8 一批全开，>8 按 8、8、余数顺序分批，上一批全部完成才启动下一批），仍可显式设为更低（同为固定分批大小）；不能承诺每件一分钟内完成。上表 2/4/8 档实测数据保留为历史突发样本，不因调度从滑动补位改为固定分批而改写。
- 真实不同素材、不同源商品、多店长时间运行可能有不同瓶颈；本次同图去重结果不能推广为这些场景的上限。
- 此次只验证草稿保存链路，不包含平台发布/审核容量。没有通过重复发布来压测线上店铺。
- 发现网络错误、限流、字段不匹配或不确定写入即停止升档；保留 taskId 和回执，不盲重试。
- 同来源复制错误延迟停止的回归测试已发现并修复：现在释放复制锁之前停止整个批次；其他在途工作收尾。修复只影响失败路径，实测成功路径的并发设置未变。
